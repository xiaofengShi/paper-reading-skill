# HarnessPro：当自我改进开始计费

深读对象：HarnessPro: Recursive Harness Self-Improvement with Pareto Optimization for Performance-Cost Trade-offs（arXiv 2610.26770v2，PDF 41 页，清华、Z.AI、上海交大、Warwick、Kling AI 合作）。Harness 递归自我改进（RSI）这一线的方法都在回答"怎么让 Agent 的编排层自己变好"；这篇论文换了一个部署视角的问法：**变好的每一步都在花钱，钱进不进目标函数？** 此前的无标签方法 RHO 在 SWE-Bench Pro 上把通过率从 59.0 提到 80.0，代价是单任务成本涨 42.6%。HarnessPro 把目标改成带性能地板的双目标 min(−PR, C)，用多智能体管线做递归进化，输出 lite/medium/heavy 三档 harness 而非单一产物：GPT-5.5×Codex 上 heavy 档三基准全部超过 RHO 且平均成本低 26.1%，medium 档在 SWE-Bench Pro 上用一半价格保住 RHO 级性能。本篇按细章深读规范逐段重构：机制逐一展开、公式逐步推导、主表逐列验算、附录 B/C/D（进化指令、智能体产物、进化后 harness 的完整配置）全部整合进正文。

## 01 / 问题：RSI 的账单从来没有进过目标函数

Harness 是模型外围的软件运行层：提示、工具与技能、上下文与记忆机制、hooks、验证策略。RSI 路线（RHO、AHE、HarnessFix、HarnessX）用历史执行轨迹诊断弱点、指导 harness 更新，但它们的目标函数里只有通过率一个变量——更强的探索、更深的验证是唯一被奖励的修改方向，token 与延迟的膨胀是"副作用"，从没有人把它请进优化目标。论文的动机数字值得亲手验算一遍：RHO 在 SWE-Bench Pro 上把成本从 \$1.88 推到 \$2.68，涨幅

$$(2.68-1.88)/1.88=0.800/1.88=42.6\%$$

分母是**旧成本**。也就是说涨掉的 80 美分是每个任务、每次运行的经常性支出。部署视角下这就不可接受了：一个通过率 80 分但单任务 \$2.68 的 harness，和一个 79 分但 \$1.26 的 harness，多数真实场景会选后者——但现有方法根本不生产后者。

于是论文的问题式（Eq. 1）是全文一切设计的源头：

$$\min_{h\in\mathcal{H}}\;\big(-\mathrm{PR}(h),\,C(h)\big)\quad\text{s.t.}\quad \mathrm{PR}(h)\geq \mathrm{PR}(h_{0})$$

三条承诺叠在一起：找的是**帕累托前沿**而不是单点；初始 harness $h_0$ 的通过率是**硬地板**；最终交付前沿上的三个代表（lite/medium/heavy）而不是一个"最优"。后文会看到，这个式子如何把整条流水线的设计串起来。

定位上也值得对齐一下（Table 1 的四维比较）：优化目标（Pass 还是 Pass+Cost）、修改范围（技能/工具还是整个 harness）、反馈来源（有无真值标签）、迭代方式（单轮还是递归）、产出（单一还是帕累托集）。此前没有一个方法同时满足"双目标+全 harness+无标签+递归+帕累托集"：SkillMOO 双目标但只优化技能文档且依赖真值；RHO 无标签但单轮、单目标、单产出；AHE 递归修改整个 harness 但需要真值。HarnessPro 的贡献是把这个组合第一次凑齐——而凑齐的难点恰恰在"无标签 × 双目标"的交点上：没有真值时性能地板怎么量、双目标时没有标准答案的候选怎么比，这分别是 §04 与 §10-11 要解的两个题。

## 02 / 三个指标各怎么算

### 通过率与三集隔离

任务通过的定义是**全部官方测试通过**（ProgramBench 例外：按官方协议取每任务通过测试比例的宏平均）。ProgramBench 的口径差异要说清：宏平均先算每个任务自己的通过比例、再对任务等权平均——一个只通过一半测试的任务贡献 0.5 而不是 0，所以它的数字与"全过式"基准不可直接比大小，只能比同基准内的相对变化。数据切三份：训练集（10 个任务，见 §05）驱动进化、验证集评估候选与选代表、测试集只在全部进化结束后评估一次。三集隔离不是走过场——§06 会看到验证集与测试集对 Planner 全程不可见，测试集指标在 Fig.  4 里逐轮画出但**仅作可视化**，不参与任何选择。

### 成本：三类 token 分别计价

$$C(h)=\frac{1}{|\mathcal{D}_{test}|}\sum_{x\in\mathcal{D}_{test}}c_h(x)$$

其中单任务成本 $c_h(x)$ 把轨迹里所有模型调用的 token 按**未缓存输入/缓存输入/输出**三类汇总后按价目表折算。价目表（Table 4，附录 A.2）值得全文抄录，因为它是后文一切美元数字的换算基准：

| 模型 | 未缓存输入 | 缓存输入 | 输出 |
| --- | --- | --- | --- |
| GPT-5.5（<272K 上下文） | \$5.00/M | \$0.50/M | \$30.00/M |
| GLM-5.2 | \$1.40/M | \$0.26/M | \$4.40/M |

这张表隐含两个结构性事实。**其一，输出比输入贵一个数量级**（GPT 侧 30 vs 5），"省 token"的重心从来不在少读而在少写；**其二，缓存命中把输入成本压到 1/10**，所以任何不破坏提示前缀（KV 缓存前缀）的修改都有额外的经济红利——§15 会看到进化产物正是这么做的。做一个教学算例感受权重结构（**构造示意，非论文数据**）：设某任务耗 0.05M 未缓存输入 + 0.30M 缓存输入 + 0.016M 输出，则成本为 $5\times0.05+0.5\times0.30+30\times0.016=0.25+0.15+0.48=0.88$ 美元——与 Vanilla 在 Terminal-Bench 2 的 \$0.89 同量级。注意输出 token 只占总 token 量的约 4.4%，却占成本的 55%：**成本的主导项是模型说的话，不是模型读的东西**。这解释了为什么进化产物里"工具输出压缩 + 精简指令"（都是减输入）之外还需要"预算 hooks 阻断拖延"（阻止无限生成的对话尾巴）。价目表还有一个容易读反的推论：GLM-5.2 的单价全面便宜（输出 \$4.40/M，约为 GPT 的 1/7），但 Table 2 里 GLM 侧 ProgramBench 单任务成本高达 \$11–17，反而贵数倍——单价便宜不等于便宜，**token 体积才是主导项**：GLM-5.2×Claude Code 的思考与长上下文消耗（每请求上限 131,072 token、2,000 轮上限）远大于 GPT 侧，量级盖过了单价差。这也再次解释了为什么成本优化在 GLM 侧收益更大（PB 上 heavy 从 Vanilla 的 \$11.34 降到 \$14.95 之外——不对，是 RHO 的 \$17.00 降到 \$14.95，相对降幅 12%），且两基座的绝对美元不可横比。

### 延迟：辅助指标

$$L(h)=\frac{1}{|\mathcal{D}_{test}|}\sum_{x\in\mathcal{D}_{test}}\big(T_{end}-T_{start}\big)$$

墙上时钟、评分时间不计。论文明确不把它放进目标：服务器负载与网络会污染它，同一配置早晚跑两遍延迟就能差出成比例——一个被噪声污染的目标会把选择压力引向运气好的那轮。但结果里它普遍改善了（SWE 上 heavy 档 520s→412s）——省 token 的动作大多也省时间，这是红利不是承诺。

## 03 / 地板约束：为什么"不伤性能"必须是硬约束

回到 Eq. 1 的约束项。如果没有 $\mathrm{PR}(h)\geq\mathrm{PR}(h_0)$，双目标优化有一个天然的下坡路：把推理力度锁到 low、砍掉全部验证、清空上下文——成本骤降，通过率也骤降，但只要它还在帕累托前沿上（更便宜但更差），选择器就没有理由拒绝它。Table 3 给了这个退化的实测版本：给 RHO 加"固定低推理力度"，Terminal-Bench 2 成本从 \$1.09 降到 \$0.45（−58.7%），通过率从 76.3 崩到 62.7。地板量的是**验证集**上的通过率（$h_0$ 用固定生成测试在 $\mathcal{D}_{val}$ 上跑出的 $\mathrm{PR}_{val}(h_0)$），不是测试集——地板本身也建立在生成测试这把尺子上，尺子的漏检会传导为地板的松动（§16 回到这一点）。它的作用是把整个搜索空间切掉一半：**只在"不比初始差"的区域内找便宜解**。这个设计在附录 B 的进化指令里还有第二重保险（§08）：指令文本明说"要真实的效率收益，而不是靠跳过必要工作、放弃困难任务或弱化验证换来的低账单"。

## 04 / 无标签评估：把判官换成一把固定的尺子

### 判官的乐观偏差

无标签设定=没有真值解、官方测试、判分器。RHO 用 LLM 对比轨迹做自偏好选择。论文的观察：LLM 判官**系统性乐观**——经常把有缺陷的实现判成成功。这不是抽象批评：合并训练任务的混淆矩阵（Fig. 2）给出量化，直接 LLM 判断的失败检出率只有 **41.7%**，即一百个失败任务里 58 个被当成成功放行。偏差的方向值得点破：判官看到的是一条"叙述自洽、步骤完整"的轨迹——模型执行得有条不紊，只是结果错了；判官评估"过程像不像成功"而非"产物真的满足要求"，于是系统性把"执行得漂亮的功能性失败"放行。在单目标 RHO 里这个偏差直接虚增感知改进：候选被高估的分数进入选择，选出的 harness 再被同样的偏差复核，误差不复原、只累积。

### 测试合成器的完整规程

HarnessPro 的替换是把 LLM 从"裁判"降级为"出题人"：

$$\mathcal{S}(x)=\operatorname{TestSynth}\big(x,\,\tau_{h_0}(x)\big)$$

输入是任务描述与**初始 harness** $h_0$ 的轨迹，一次性生成后**全程固定**。附录 C.3 的部署规程比正文详细得多，四个要点值得展开：**证据边界**——只读 public-task.json、public_inputs 与只读的初始产物，产物"只是实现与执行诊断的上下文，永远不是答案钥匙"，明令禁止寻找官方测试/判分器/解法（本地或在线）；**出题纪律**——覆盖文档化的行为、有效替代、边界与合理组合，"不要为了凑满固定数量发明额外义务"——凑数的用例只会稀释尺子的分辨力；**oracle 选择阶梯**——优先公共参考 > 已知答案 > 必要内容性质 > 可判别的元变换关系（元变换指"对输入做一类已知变换、输出应按同样规律变化"的性质，它不需要知道标准答案也能判对错），且"永远不从被测产物推导期望常数、哈希或容忍值"（否则测试就成了循环论证）；**执行语义**——status=ok 而 passed=false 是"合法执行+产品失败"，让产品通过不是目标；infra_error 才是待修的测试缺陷，且只修"被证实的缺陷"、不跳用例、不捕获所有异常、串行执行。输出契约固定为恰好 10 个用例 + 清单（每例标注 behavioral/format/unavailable_oracle）+ 覆盖记录（**含"没检查什么"**）+ 修复日志。

### 为什么从 $h_0$ 的轨迹出题

测试合成的输入是初始 harness 的轨迹而非各候选的轨迹，这是设计而非便利：若从候选轨迹出题，测试会随候选漂移，"固定"就名存实亡。$h_0$ 轨迹在这里的角色被规程严格限定——它是"实现与执行诊断的上下文"，帮助出题者理解任务的输入输出接口长什么样，但"永远不是答案钥匙"：期望值必须来自公共证据（文档、已知答案、内容性质），不从产物推导。这留下一个隐含的边界：$h_0$ 越弱，其轨迹能提供的接口信息越少，出题质量越依赖任务描述本身——论文的 $h_0$ 是 Vanilla（原始 Codex/Claude Code harness），已是不弱的起点；对极弱初始 harness 的行为，论文未做检验（§16）。

### "固定"的两重作用

固定测试既是公平性机制（所有候选被同一把尺子量），也是防作弊机制：进化不能通过"让判据变松"伪造进步——这恰是 RSI 可信框架里"修改改进机制"风险的工程化防御。换用固定测试后失败检出率升到 **83.3%**。混淆矩阵原文：

## 05 / 训练集怎么挑：难度加权的 DPP coreset

### 核的构造

进化每轮要跑 候选数 × 10 任务 × G=3 遍，训练集必须小而有代表性。选法沿 RHO：LLM 判官给每个候选任务打难度分 $r_i\in[0,10]$ 与**失败模式指纹** $\phi_i$（刻意抹去任务专名，使相似度反映共性困难而非项目表面），然后构造难度加权 DPP 核（Eq. 10）：

$$w_i=\Big(\frac{q_i}{\max_j q_j}\Big)^{\alpha},\qquad q_i=\max(r_i/10,\varepsilon),\qquad K=\operatorname{diag}(w)\,S\,\operatorname{diag}(w)$$

其中 $S_{ij}=u_i^{\top}u_j$ 是指纹余弦相似度，$\varepsilon=0.1$（难度下限，防止 $r_i=0$ 的任务权重直接归零而彻底丧失被选可能），$\alpha=\theta/2(1-\theta)$ 取 $\theta=0.7$ 得 $\alpha\approx1.167$——这个指数形式使权重对难度的敏感度介于线性与平方之间。

### 难度权重手算

取两个任务 $r=8$ 与 $r=3$（**教学算例**）：$q$ 为 0.8 与 0.3，权重比

$$w_8:w_3=1:(0.3/0.8)^{1.167}=1:0.375^{1.167}\approx1:0.32$$

难度低一档，核权重掉到三成；又因 $K=\operatorname{diag}(w)S\operatorname{diag}(w)$，任务对的联合行列式再乘 $w_iw_j$——**指纹相似且难度低**的任务几乎不可能进 coreset。直觉上，DPP 的行列式是子集在指纹空间里张成的"体积"：抓两个指纹几乎相同的任务，体积近似为零；难度权重相当于先给每个方向乘一个增益，困难任务的方向被放大。所以 coreset 是"困难且彼此不像"的十个任务——这正是诊断想要的原料：困难才有失败可分析，彼此不像才能覆盖不同失败模式。

### 贪心而非采样

标准 k-DPP 给每个 k 元子集的概率（Eq. 11）是 $\Pr_k(Y)=\det(K_Y)/\sum_{|Z|=k}\det(K_Z)$；实现上不做分布采样，而是贪心地逐个加入使行列式最大的任务（Eq. 12）逼近众数子集。最终 coreset 固定 10 个任务——这个规模的代价与风险在 §16 讨论。

## 06 / epoch 循环总览：Algorithm 1 逐段走查

整个框架是一个三阶段循环，初始化只有四件事：收集 $h_0$ 在 train∪val 的轨迹；对每个任务生成固定测试 $\mathcal{S}(x)$（一次生成，永不再改）；用 $\mathcal{S}$ 量出 $h_0$ 的验证通过率立为地板；候选集 $\mathcal{A}_0=\{h_0\}$。此后每轮：

**阶段一（诊断）**：每个候选在 10 个训练任务上各跑 $G=3$ 条独立轨迹，Analyzer 联合检查轨迹与指标（§07）；**阶段二（生成）**：每个候选 × 三种优先级指令出三份计划（§08），Editor 在独立工作区各落一个可执行 harness、Git 提交，新候选与父代合并成 $\widetilde{\mathcal{C}}_t=\mathcal{A}_t\cup\mathcal{C}_t$；**阶段三（评估选择）**：每个候选在验证集每任务跑一次、固定测试判分，先滤掉破地板或被支配者，再为三档各选一个代表组成下一轮 $\mathcal{A}_{t+1}$（§10–11）。轮数：TB2 与 SWE 各 3 轮、ProgramBench 4 轮；候选集每轮最多 3 个（三档代表），因此每轮产生至多 3×3=9 个编辑候选，加上 3 个父代共至多 12 个 harness 要在验证集上各评估一遍——验证集规模直接决定每轮的评估账单，这也是训练侧只用 10 任务做诊断、把大批任务留给验证的原因之一（诊断要 G=3 遍重复，单任务成本是验证的 3 倍以上）。

每条 rollout 同时记录三元组指标 $m_h^{t,g}(x)=(\mathrm{Pass},c,\ell)$ 并保留 token 用量与工具调用明细——这些明细是 Analyzer 区分"必要计算与可避免开销"的原始证据，也是 Planner 评估修改预期收益的依据。防泄漏的设计清单在此集中核对：train/val/test 三集隔离；测试从 $h_0$ 轨迹生成后冻结；Planner 不见 val/test、默认不见全轨迹（按诊断里的路径调阅）；验证评估每任务单次 rollout；基础设施失败剔除并重试（不把崩溃计为失败）；测试集评估只在进化结束后做一次。

## 07 / 诊断：三条轨迹联合看，成本问题与失败问题并列

$$z(h,x)=\operatorname{Analyzer}\big(x,\{(\tau_h^{t,g}(x),\,m_h^{t,g}(x))\}_{g=1}^{G}\big)$$

Analyzer 的输出是结构化的问题清单：每条问题含**问题描述、对性能与成本的影响、证据定位**（轨迹文件路径+事件行号区间），按任务汇总超 64K token 再摘要一层。附录 C.1 给了两份真实产物，恰好展示诊断的两种形态。

### 失败侧样例：Caffe–CIFAR-10

任务"构建 CPU 版 Caffe 并训练 CIFAR-10 五百轮"，三条轨迹全部在训练前止步。诊断给出五条问题：**Issue 1（共享瓶颈）**：三轨分别卡在 protobuf 修复、Caffe 已建成但在下载数据集、OOM 后重建中——"全部止步于训练前"这个共性被从三条不同表象里抽象出来；**Issue 2（成本）**：`make -j$(nproc)` 高并行编译在每条轨迹都触发 OOM，失败的编译轮次是纯浪费；**Issue 3（个别失速）**：最先进的一条打断单流下载换 aria2 并行下载，装好了工具却在下载中结束；**Issue 4 最值得注意——一个"未观察到的下游风险"**：一条轨迹的 Caffe 配置没开 OpenCV，而标准 CIFAR 流程的 compute_image_mean 需要 OpenCV，"如果跑到那一步大概率会失败"——诊断不只记录已发生的失败，还推演**将要发生**的阻塞并给出证据行号；**Issue 5（无害扰动）**：误用不存在的 1.0.0 分支后自行检查 tags 改用 1.0，标注为"增加了命令但无持久质量损失"。这份清单给下游 Planner 的信号非常具体：这里有可避免的编译浪费（Issue 2）、有下载策略问题（Issue 3）、有配置缺陷（Issue 4）——每条都同时标注了质量影响与成本影响。

### 成本侧样例：Mailman

对照样例是 Postfix/Mailman 3 邮件列表配置任务，三条轨迹**全部通过**生成测试，但诊断照样列出问题：探索远超相关配置的范围（把与任务无关的系统状态也检查了一遍）、对同一配置点的重复检查、以及两次不改结局的绕路（装了不必要的组件又回退）——全部标注为"增加成本而不改变最终结果"。这显示了双目标框架下的诊断视角：**通过的任务也要审账**。RHO 式单目标管线没有动机为全过的任务写诊断。

## 08 / 计划：三条指令的原文哲学与真实产物

$$\mathbf{p}_j(h_i^t)=\operatorname{Plan}\big(I_j,\,h_i^t,\,\mathbf{z}(h_i^t),\,\mathbf{m}(h_i^t),\,\{(\operatorname{Diff}(h_i^t,h_k^t),\,\mathbf{z}(h_k^t),\,\mathbf{m}(h_k^t))\}_{k\neq i}\big)$$

### 附录 B 的三条指令说了什么

三条指令（$I_1$ 省成本 / $I_2$ 平衡 / $I_3$ 重性能）的原文比"优先级不同"这个概括有信息量得多。$I_1$ 的核心句："**追求真实的效率收益，而不是靠跳过必要工作、放弃困难任务或弱化验证换来的低账单**……更少的步骤或更短的输出本身不构成改进"；$I_2$："把正确性与效率当**联合目标**……平衡的计划应当改进权衡，而不是简单平均另外两个方向"；$I_3$："把投入集中在能解决**实质性失败**的地方，而不是在所有任务上均匀加算力……不要假设更复杂的 harness 就是更有能力的 harness"。更关键的是三条共有的元要求："这些都是可选的搜索方向而非清单——从证据推导机制，**不要预设路由规则、固定阈值、档位分类法或逐任务规则**"。这一点常被误读：论文正文 §5.3 展示的五档执行档位**不是设计者写死的**，而是 Planner 在证据下自己长出来的——指令只给方向与边界，机制由数据决定。为什么要把话说得这么死？因为一旦指令预设了机制（比如"做一个路由器"），Planner 就会照做——进化将收敛到设计者的想象而不是证据；且预设机制在错误基准上是系统性浪费（§15 的 ProgramBench 产物证明了这种担心的现实性：那个基准上根本不该有路由）。§15 会看到三基准进化出的产物结构确实不同。

### C.2 的计划样例

一份 medium 系计划的实际内容：新增 `router_prompt.txt`（按任务公开特征选 low/medium/high/xhigh 推理力度，要求 JSON 输出+理由）、`guarded-run` 工具（超时控制+全量日志落盘+只回显退出码/耗时/日志路径/有界首尾摘录）、`quick-probe` 工具（一次性环境快照：目录、git 状态、常用工具可用性）、`runtime.json` 设 tool_output_token_limit=12000。注意其风险栏的诚实措辞："路由器可能给看似简单的任务欠配力度；在很小的任务上，这次分类调用本身可能是净负收益"。另两份样例：heavy 系计划强调"从公共任务先导出验收清单、绝不使用基准答案/判分器"；lite 系一份后代计划专门回应"路由器频繁选择 high/xhigh"的实测过度分配。

### 跨候选借鉴

Planner 输入里的 $\operatorname{Diff}(h_i^t,h_k^t)$ 让三系候选互相看到彼此的代码差异与诊断——lite 系验证过的省钱机制可以被 heavy 系计划吸收，反之亦然；但 $I_2$ 明确要求"比较同侪以理解强弱与交互，而不是整体照抄机制"。

## 09 / 编辑与评估：Git 兜底的可回滚进化

$$\widetilde{h}_{i,j}^{t}=\operatorname{Edit}(h_i^t,\mathbf{z},\mathbf{p}_j),\qquad \widetilde{\mathcal{C}}_t=\mathcal{A}_t\cup\bigcup_i\{\widetilde{h}_{i,1}^t,\widetilde{h}_{i,2}^t,\widetilde{h}_{i,3}^t\}$$

三份计划各自在独立工作区实现（互不污染），产物提交 Git——变更可追溯、可回滚、Diff 可被下一轮 Planner 直接消费。评估侧：每个候选在验证集每任务**一次** rollout，按固定测试判分得 $(\mathrm{PR}_{val},C_{val},L_{val})$；基础设施失败（容器崩溃、网络断连等）剔除重试，不混入失败统计。

## 10 / 过滤：地板之上、支配之外

$$\widetilde{\mathcal{A}}_{t+1}=\Big\{h\in\widetilde{\mathcal{C}}_t\;\Big|\;\mathrm{PR}_{val}(h)\geq\mathrm{PR}_{val}(h_0)\;\land\;\not\exists h'\in\widetilde{\mathcal{C}}_t:\;h'\prec h\Big\}$$

$h'\prec h$（帕累托支配）= $h'$ 两指标都不差且至少一项严格更好。手算一个小例（**教学算例**）：候选甲 $(74.0,\,0.9)$、乙 $(74.0,\,1.2)$、丙 $(71.0,\,0.5)$（美元），地板 72。乙被甲支配（同分更贵）出局；丙便宜但 71<72 破地板出局——**便宜救不了不及格**，这正是地板与支配过滤的分工：地板管"不许差"，支配管"不许又贵又不更好"。注意支配的边界情形：两候选两指标全部相等时互不支配、双双保留——它们对下一轮是等价起点；而"一项相等一项更好"构成严格支配，相等者出局。过滤后集合可能少于三个（论文脚注明说实践中常发生），此时某些档位会共享同一个代表。

## 11 / 代表选择：归一化加权平方距离的算术

### 归一化

$$d_{perf}(h)=\frac{P_{max}-\mathrm{PR}_{val}(h)}{P_{max}-P_{min}},\qquad d_{cost}(h)=\frac{C_{val}(h)-C_{min}}{C_{max}-C_{min}}$$

极值取自**当轮过滤后集合**，把两个指标折成"离最优的归一化距离"。注意这个选择让度量随前沿一起移动：第一轮的前沿和第三轮的前沿不同，但每一轮的"离最优距离"都在 $[0,1]$ 内可比——选择标准是相对的，不锚定绝对分数。副作用是当集合缩小时（比如只剩一个候选）归一化分母趋零，此时选择退化为平凡——实践中过滤后至少保有 Pareto 前沿上的若干点。

### 三档手算

附录 A.2 给出权重：lite $(\alpha,\beta)=(1,2)$、medium $(1,1)$、heavy $(2,1)$，全程固定。选择目标（Eq. 9）：

$$J_m(h)=\alpha_m\,d_{perf}(h)^2+\beta_m\,d_{cost}(h)^2$$

手算（**教学算例**）：过滤后剩甲 $(72.0,\,0.40)$、乙 $(76.0,\,0.50)$，则 $P_{min}=72,P_{max}=76$、$C_{min}=0.40,C_{max}=0.50$，$d_{perf}$：甲 $=1$、乙 $=0$；$d_{cost}$：甲 $=0$、乙 $=1$。lite：$J_甲=2\cdot0=0$，$J_乙=2\cdot1=2$ → **选甲**；heavy：$J_甲=2\cdot1=2$，$J_乙=1\cdot1=1$ → **选乙**；medium：$1=1$ 对称并列（连续真值下几乎不会发生，仅供演示对称点）。

### 为什么是平方

线性加权和 $\alpha d_{perf}+\beta d_{cost}$ 会偏爱单边极端点（全押性能或全省钱）；平方项惩罚"两头都差"也惩罚"偏科"，倾向挑帕累托前沿上**两边都不太差**的折中位置——恰好是三个部署档位各自的性格。每轮为三档各留一个代表还让下一轮搜索在三个预算区域各有一粒种子，这是"输出帕累托集"的机制落点。

## 12 / 主结果：把每个百分比验算回去

### 六条基线各控制什么

先把对照组的身份摆清，否则数字读不出归因力。Vanilla 是优化起点（原始 Codex/Claude Code harness）；Dynamic Cheatsheet 维护跨任务复用的策略与代码片段本；ReasoningBank 从历史轨迹蒸馏策略库按任务检索；Sleep-time Compute 在查询到来之前预先对上下文做推理、把结论存成可复用记忆——这三条代表"记忆/经验复用"路线，不修改 harness 本体。RHO 是最接近的前身：轨迹分析指导修订技能与工具、LLM 自偏好选候选、单轮单目标。Balance 只把 RHO 的优化指令改成双目标（框架不动）——它拆开"指令"与"框架"的贡献；RHO+Iteration 让 Balance 跑满与 HarnessPro 相同的轮数——它拆开"递归"与"双目标机制"的贡献。这两个变体是全文归因设计的支点：若 Balance 就够用，HarnessPro 的多智能体框架就是多余的；若 RHO+Iteration 能追平，双目标选择机制就是多余的。结果（§13）显示两者都不够。

### 三档的部署性格与 CoP 重算

SWE 上：lite \$0.80/72.3、medium \$1.26/79.0、heavy \$1.97/80.7。medium 对 RHO 的账 $(2.68-1.26)/2.68=53.0\%$ 降幅、只让 1.0 分——"半价平替"的出处。lite 对 Vanilla 的三笔：TB2 $(0.89-0.43)/0.89=51.7\%$、SWE $57.4\%$、PB $17.7\%$，即论文的"17.7–57.4%"区间。Table 3 还报 Cost-of-Pass（CoP=成本/成功任务数），这个量可以直接验算：TB2 heavy $0.72/0.808=0.89$、RHO $1.09/0.763=1.43$、medium $0.56/0.763=0.73$、lite $0.43/0.729=0.59$——与表格逐个吻合；CoP 把"分数的代价"折到单个成功上，heavy 的 CoP 优势（0.89 vs 1.43）比原始成本差更刺眼。

## 13 / 演化动态：双改善常要等到第二轮之后

Fig. 4 逐轮画测试集指标——注意这些中间点只用于展示演化轨迹，任何一轮的过滤与代表选择都只用验证集数字，测试集曲线如果反过来影响选择就构成泄漏，论文在图注里专门声明了这一点。TB2 的 heavy 一路双改善：74.6/\$0.91 → 80.8/\$0.72；lite 与 medium 第 2→3 轮守住分数继续降本（\$0.61→\$0.43、\$0.68→\$0.56）。最有信息量的是 SWE medium 的三轮：70.0/\$1.57 → 77.0/\$1.66（涨分也涨钱）→ 79.0/\$1.26（双改善）。**单轮进化常只买到"分或钱"之一**；双改善是递归多轮+帕累托选择压力的产物。对照 RHO+Iteration（同轮数、单目标指令）：TB2 上 medium 与它同分（76.3）但便宜 $(0.82-0.56)/0.82=31.7\%$，SWE 上它 80.0/\$1.90 仍被 heavy 80.7/\$1.97 在分数上压过，PB 上 heavy 比它高 1.3 分再便宜 5.8%。读法要点：RHO+Iteration 证明了"多跑几轮"本身也能省点钱（TB2 从 1.09 降到 0.82），但它的选择器是单目标的，每轮只朝一个方向收敛，永远到不了前沿的另一半——同轮数救不了单目标，功劳在双目标规划与前沿筛选。ProgramBench 的第 4 轮各档继续降本保分，说明在任务同质度高的基准上，多轮递归的价值形态不同：不是继续涨分，而是持续挤出同质任务上的冗余开销。延迟维度再补一笔：medium 档在 TB2 上 253s、SWE 上 326s，均低于 RHO 的 354s/437s——成本优化经由"少生成、少重复检查"几乎必然带出速度收益，但论文不承诺它，读者也不应把它当选择依据。

## 14 / 消融：尺子与药方各值多少

CoP 也让消融更可读：SWE medium 去 Planner 后 CoP 从 \$1.59 涨到 \$1.95——每个成功任务贵了 23%，因为掉分与涨价同时发生。去 Planner：SWE medium 79.0/\$1.26 → 73.0/\$1.42——**分数掉、钱反升**，说明三档计划是"找到双改善方向"的来源，没有它编辑只在单方向上用力。去测试合成器：三档全线掉 3.4–10.0 分（heavy TB2 80.8→74.6），掉幅最大——**尺子不可靠一切白搭**，这是无标签框架的承重墙。更有归因力的是"RHO 抄单机制"三变体：+动态路由（TB2 76.3/\$0.92、SWE 76.0/\$2.13）、+预算 hooks（76.3/\$0.92、75.0/\$1.75）都省钱但都掉分；+固定低力度掉最惨（62.7/\$0.45）。三个变体全部被 HarnessPro 帕累托支配——双改善是**组合机制+递归选择**的涌现性质，把任何单件搬到单目标框架都退化为单边受益。

## 15 / 进化解剖：钱省在哪（附录 D 全量）

### 五档执行档位与门控路由

TB2 medium 进化产物是四个文件：`model_instructions.md`、`profile_rubric.md`、`policy.json`、`hook.py`。**一个独立的 GPT-5.5 调用**按 rubric 从任务描述选五档之一，policy 落参数，hook 执行预算。五档（medium 模式）：compact（low 力度，收敛≈4 次调用/停止≈8）、lean（low，10/16）、standard（medium，26/38）、deep（high，30/48）、research（high，约 40 次）。rubric 的门控顺序 compact→research→deep→lean→standard，其中两处设计高于直觉：**"未知决定性证据默认 standard"**（信息不足不许降档）；**强 oracle 的定义极其严格**——必须显式可本地重复且提供局部化失败/定量误差/候选排序/确定性仿真之一，"编译通过、端口开了、跑通一次端到端"明确算弱证据。deep 档列出九种适用形状并同样列出不适用清单——适用侧的公共内核是"存在可局部验证的强假设生成-检验循环"：潜结构/参数恢复（有精确兼容性或定量目标）、跨多组件的状态一致性（可用不变量或往返检查）、损坏结构状态恢复（竞争性格式/排序假设）、带可执行评分器的约束合成、从大量观测做精确候选验证的恢复/推理/攻击、带确定性模拟器的逆问题、确定性变换下的候选构造、双语法双重有效性、严约束下的参考行为重实现；不适用侧一句话总结：**术语查证、长规格阅读、普通性能调优、普通逆向、只有隐藏测试**都不是 deep——以及"deep 需要容得下几次**改变证据的迭代**"，如果评估本身吃掉大半个时限，再强的 oracle 也支撑不起 deep。compact 门控同样列了五种形状（视觉/隐藏状态的长串行交互、不可用的账号设备凭据、宽泛隐藏行为+端到端接受拒绝联合目标、单工件跨多语法仅联合反馈、无量化比较器的海量媒体判读），并强调"难、可视化、专项化、虚拟化本身不够格"。

### hook.py 逐段

预算不是建议是硬闸：`_pre_tool_use` 计数超过 `finalize_after_tools` 时直接 `permissionDecision: deny`，拒绝语是行为指令："**保留当前文件，停止调用工具，基于现有证据给出最佳最终答案**"。两段阶段提醒：`economy_after_tools` 处触发"经济期开始：批量独立检查、停止过程叙述、不重复未变的检查、**不要拿任务要求的行为验证或精确终态检查做交易**"；`strict_after_tools` 起每 `strict_reminder_every` 次重申"收敛期：停止广泛探索……若有具体失败未解或交付物被改，**修复它而不是因为进入该阶段就收尾**"。`_compact_text` 做行级去重（重复超过 2 行折叠为"[前行又重复 N 次]"）+首尾截断。

| --- | --- | --- | --- | --- | --- |
| compact | low | 2 | 4 | 14 | 2 |
| lean | low | 6 | 10 | 22 | 4 |
| standard | medium | 14 | 26 | 44 | 8 |
| deep | high | 16 | 30 | 54 | 8 |
| research | high | 8 | 20 | 46 | 6 |

工具输出统一压缩：history_token_limit 900、max_chars 4000（head 2400/tail 900）、rtk_enabled。正文说的"14/26/44"即 standard 行。**rubric 的"停止≈38"是软目标，hook 的 44 才是硬闸**——双层预算，软硬分离。

### lite/heavy 与另两个基准的差异

lite 只改 policy：deep/research 力度 high→medium、各档 finalize 全线下调（14→8、22→16、44→38、54→48、46→40）——同 rubric 同 hook，靠参数降档。heavy 反向：rubric 与 policy 双双上调——compact 变 4/8/14、lean 升为 medium 力度 10/22/36、standard 升为 high 力度 18/38/60、deep 20/42/68、research 16/36/60——lean 门槛放宽到"约 12 次或更少证据调用"，指令里加强多阶段服务的外部入口验证与"收尾前重读公共任务一遍、对照独立证据核对每项要求"。**SWE 产物多了两件 TB2 没有的东西**：`bin/repair-verify`（通用代码检查脚本）与 `checklists/contract-verification.md`（逐项契约核对清单），工作流是一套仓库修复的契约化纪律：先把 task/prompt.md 当**契约**读、为一组"精确公共名字"（文件、负载、默认值、错误行为、兼容性要求、明说的边界情形）记账本；改动前先查本地 git 历史、tags、上游提交、相邻实现——"已知修法优先适配，不猜"；做满足契约的**最小生产源码改动**；预留预算给改后任务形态测试与最终 diff 核对，"仅编译通过不足为凭"；生成物、缓存、临时测试不得进最终补丁。**ProgramBench 产物则完全没有路由**：固定 GPT-5.5 high 力度，取而代之的是七步"证据优先重建流程"：把随附文档全部读成**行为台账**（命令、旗标、输入输出、退出码、文件效应、默认值、错误行为、格式、明说的边界）；尽早立起 compile.sh 与最小可执行骨架、先跑通完整构建-运行循环；只经公共接口对参考实现做**小判别性探针**、记录实测而非按程序名臆断；先广度后打磨（快乐路径与常见输入类优先）；自建用例双向对拍，分歧要**约化出一般规则**而不是打特例补丁；**定期从干净状态重建**——依赖缓存产物、未声明工具或提交目录外文件的"解"不算完成；最终离线验证 compile.sh 可执行、代表性成败探针与参考一致。三基准产物结构不同恰好证明附录 B 的元约束：机制由证据决定，没有预设模板。读者复用这套框架时也可以据此预判：你的基准任务如果高度同质，进化的产出大概率是"流程纪律"而不是"路由结构"；异质任务集合才会养出门控路由这类自适应机制。

## 16 / 证据的边界

四条边界。**尺子上限**：83.3% 检出率意味着约 1/6 失败被漏检，且漏检不是随机的——固定 10 个用例的预算天然偏向行为主路径，风格退化、性能回归、用例没覆盖的部分行为这类失败最容易被放过；出题又只看得到 $h_0$ 的一个实现视角，接口的未见侧面可能根本没人测。进化过程中的地板与支配判断建立在这把有误差的尺子上——靠测试集官方测试的最终评估兜底结论，但**进化路径**可能被误导；**coreset=10**：诊断覆盖面系于 DPP 选样，未见失败模式进不了诊断；**成本口径**：固定价目+各基座缓存行为不同，跨基座不可横比；CoP 与成本的换算依赖价目表时效；**结论范围**：heavy 在 SWE 的 +0.7 分在噪声量级，三基准都是"任务-工件-通过"型，对话式或开放探索型任务未覆盖。复现条件方面附录 A.2 齐备：默认力度（GPT-5.5 全程 high；GLM 在 TB2/SWE 用 max、在 PB 降到 high 因 max 会拖长执行）、求解器时限（TB2 原生 600–3600s；SWE GPT 1200s/GLM 7200s、判分 3600s；PB 求解 7200s+判分外层 14400s）、环境（8 CPU/32GiB）、生成参数（Codex 走 Responses API 不显式设温度与 top-p、GPT-5.5 单响应最大 128K 输出 token；GLM temp 1.0、TB2/SWE 用 top-p 0.95 与 131,072 max_tokens，PB 改 top-p 1.0、32K token、2,000 轮上限——PB 的收紧再次指向思考型执行的体积问题）。评测侧温度 0.7/top-p 0.95、每基准至少两次运行取均值（TB2/SWE 三次、PB 两次），HarnessPro 的波动以样本标准差呈现在 Table 2。

## 17 / 接回论证

把链条合上：**换尺子**（固定生成测试，检出率翻倍且封死改判据的自欺）→**三向施压**（三优先级计划让每轮搜索同时朝性能与成本两个方向探索）→**前沿筛选**（地板+支配过滤保证只进不退，平方距离把前沿落成三个可部署代表）→**产物证据**（进化出的不是"少读点上下文"而是档位路由+硬预算闸+输出压缩+契约核对的组合，且三基准各自长出不同结构）。RHO 证明了无标签 harness 进化能涨分；HarnessPro 证明同一套原料在目标函数里放进钱之后，能同时把"更好"与"更便宜"做出来——自我改进从能力问题推进到了经济问题，而部署要的正是后者。留下的问题同样清楚：生成测试的尺子还能不能再准（83.3% 不是上限）、coreset 能不能扩到更便宜的评估预算所允许的规模、以及当被优化的 harness 本身开始生成评估用的测试时，这把尺子与被测者的边界要怎么守住——最后这一问，正是 RSI 可信框架留给这个方向的下一题。
