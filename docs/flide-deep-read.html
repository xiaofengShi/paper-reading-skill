总评

这篇论文处理的是 LLM agent 技术栈里一个正在成型的裂缝：决策模型（Jev、Open-Jev、StartLux 等）以「读长上下文、输出离散选项的概率分布」为工作形态，是路由、响应评估、agent 下一步选择这类高频微决策的专用件；但 vLLM 和 SGLang 这一代推理引擎是为文本生成设计的——它们的基本工作单元是单条线性序列，于是要么把每个问题当独立 prompt 反复计算共享上下文（慢，混合架构上前缀缓存只能在块边界恢复循环状态），要么把所有问题拼进一条序列加分隔符（快，但分隔符 token 进入每个问题的输入，污染概率分布）。作者把这两种失败的根因统一诊断为「请求的逻辑结构与物理执行的耦合」，然后给出一个同时解决效率与精确性的引擎。

最打动我的是这篇论文的证明意识。系统论文常见做法是给近似正确性一个直觉论证，而这里给了 Proposition 1 的逐层归纳证明（精确算术下每个问题算出的隐藏状态与单独前向完全一致，附录 A），配一套浮点层面的验证梯队（内核级对 PyTorch 参考、前向级对 float64、每次引擎改动都要过）。「快」在推理引擎论文里不稀奇，「快且与 float32 参考的逐答案一致率最高、可选模式下位级确定」才是这篇的护城河——因为决策模型的下游是带阈值动作（概率过 0.5 就执行），1% 的概率漂移在阈值附近就是翻转。

与本周阅读线的连接尤其紧密：附录 Table 18 列出 Flide 支持的 29 个决策模型，其中就有上周深读的 Drex v1.5（9B，Qwen3.5 底座）——Flide 服务它比原厂 transformers 引擎快 2.95-7.44 倍。上周的图景是「决策模型便宜但不快」，这一篇补上服务层：便宜 × 快 × 精确三件套在 agent 基础设施层合龙。

§01 背景：决策模型与 System One 工作负载

论文开篇把决策模型放进 LLM agent 系统的实际位置：路由请求、评估响应、决定 agent 下一步。这些任务有三个共同特征——上下文长（一段对话或一条 agent 轨迹）、输出是离散选择上的分布而非自由文本、每个被路由的请求和每个 agent 动作都要过一遍。生成 token 来做分类选择既浪费算力又增加延迟，于是 Jev 与各专用决策模型出现：读完整上下文，对每个问题输出选项上的概率分布，由严格阈值直接消费这些概率。

这种负载对引擎的要求可以概括为一句话：又快又准。快是因为它部署在每个请求的必经之路上；准是因为阈值动作对概率漂移零容忍。论文引用的 Decision Index 是这类模型的能力基准，而本文的全部实验负载里都包含它的采样。

值得强调的是作者对工作负载形态的刻画，这直接决定了后面的设计：一个决策请求 r=(s,q1,…,qQ)r = (s, q_1, \ldots, q_Q)r=(s,q1​,…,qQ​) 由一个 LsL_sLs​ token 的状态和 QQQ 个问题组成，每个问题 qjq_jqj​ 有 ∣qj∣|q_j|∣qj​∣ 个 token。状态是共享的躯干，问题是分叉的枝条——这个树形逻辑结构是负载的本相，也是后面一切设计的出发点。

§02 现有引擎的三重失配

论文用 Figure 1 把三种执行方式摆在一起：同一请求（状态 + 三个问题）分别交给生成引擎、multi-item scoring 和 Flide。这张图值得细读，因为它把「快」与「准」的两难画成了一条物理序列的排版问题。

第一重：独立序列的重复计算。 vLLM 与 SGLang 的决策端点把每个问题当独立 prompt：渲染、分词、调度各来一遍，共享上下文被计算 QQQ 次。最新的 vLLM 已经支持先把请求的共享上下文算一遍再答问题，但每个问题仍以自己的序列从前缀缓存恢复——而混合架构（Qwen3.5、Gemma 4 这类在多数层用 Gated DeltaNet 的模型）上，缓存只能在块边界恢复循环状态，每个问题、每个 agent 步骤都要把最后一条边界之后的 token 重算一遍。块边界这个坑值得多解释一句：注意力层的缓存键值可以按 token 粒度恢复，GDN 的循环状态却只在分块处理时于块间落盘，前缀若不在边界上，恢复就得回退到上一条边界重算尾巴——问题越短、问题越多，这个尾巴占的比例就越大，等于把缓存的好处按比例吐回去。

第二重：multi-item scoring 的分隔符污染。 SGLang 的 MIS（multi-item scoring）走另一条路：把所有问题拼进一条上下文，每个问题前插一个分隔符 token。它确实只算一遍状态，但每个问题的输入里多了这个分隔符——它改变隐藏状态，进而扭曲输出概率，与单独提问的结果不可比。这不是工程瑕疵而是原理性的：输入变了，函数值当然变。污染的传导路径在混合模型上格外直接：分隔符 token 先被短因果卷积混进问题开头几个 token 的表示，再经 GDN 的递推写进整个问题段的状态，最后在输出头的 logits 上留痕——一个 token 的修改沿两层机制放大到整段输出分布。论文后面用数据说话：MIS 的答案与 float32 参考的总变差距离是 Flide 的约 12 倍，最多翻转 29% 的分类决策。另有一层工程代价：MIS 的 GDN 分支元数据在 CPU 上构建、CUDA 图必须关闭，吞吐优势也被抵消。

第三重：动态批次的数值漂移。 即使前两重都不考虑，动态 batching 下浮点求和的顺序随批组成变化，同一请求在不同服务器负载下可能得到不同决策。对一个阈值直接作用于概率的系统，这意味着「白天高峰与凌晨低峰的路由决策不一致」——这是可靠性问题，不只是性能问题。

§03 根因诊断：逻辑树与物理流的耦合

论文的贡献之一是把上面三重失败追溯到同一个根因：决策请求的逻辑结构（树）与物理执行结构（线性序列）被绑死了。生成引擎把逻辑结构强加给物理结构——每个问题一条序列，于是躯干被复制 QQQ 份；MIS 把物理结构强加给逻辑结构——树被写进序列本身，分隔符进入每个分支的输入。两种绑法各修一头、坏另一头。

正确的目标形态是：分支一起跑（快），但每个分支算的还是它单独跑时会算的东西（准）。物理流必须把并排摆放的分支在计算上隔离开。全注意力层可以用 mask 隔离，但 Gated DeltaNet 层没有 attention matrix 可 mask——它把之前所有 token 折叠进一个固定大小的循环状态 SSS，同一序列里的两个问题会通过这个状态互相污染。所以真正的难点在混合架构：让每个分支在计算躯干的那一遍 pass 内部，从躯干末尾的精确状态重启。

这个诊断的价值超出本文：任何「共享前缀 + 多查询」的负载（路由、重排序、多问阅读理解、agent 步进）都踩同一个坑。

§07 Proposition 1：精确性及其归纳证明

把上面两层拼起来，论文给出核心命题：因果模型在精确算术下，Flide 在问题 qjq_jqj​ 任意 token 处算出的隐藏状态，与模型单独处理 s⊕qjs \oplus q_js⊕qj​ 时在该 token 的隐藏状态完全相同，与同轮其他请求、其他问题无关。

我喜欢这个证明的地方在于它把「正确性」从内核测试提升到了结构性质：等式对任何扁平排版、任何轮次组合、任何请求混合都成立，因为没有任何一步涉及本轮的其他请求或问题。浮点层面差异留在舍入量级，附录 G 的测试梯队每次引擎改动都要过：内核对 PyTorch 参考在所有头数、滑窗、round 布局下误差停在 float32/bfloat16 舍入水平；前向对 float64 的最大误差不得超过 transformers 库误差（6.0×10⁻³ 量级）的两倍；eager 前向、CUDA 图、图内合并重放、带图像视频、从保存状态恢复，全部要落在这个界限内。「每次改动都过一遍」——正确性在这里是持续测试的产物，不是一次性的证明仪式。

§08 扁平图执行：形状只依赖流长

第二个挑战是 GPU 启动开销。一个短决策请求只占几毫秒 GPU 时间，逐个启动几千个 kernel 的话，启动本身就成了主要成本。CUDA 图能消掉这些启动，但捕获的图固定了每个 kernel 的形状，而服务器每轮遇到的请求组合千变万化——这是 CUDA 图与传统动态 batching 的经典矛盾。

Flide 的解法优雅在把树的形状从 kernel 形状里完全剥离。所有由轮次组成决定的变量——段长、位置下标、键范围、状态索引——全部住进紧凑的设备端缓冲区，kernel 从缓冲区里读自己的工作量。于是每次启动的形状只取决于流的长度这一个数。服务器初始化时按流容量捕获一族扁平图，每族再预留固定的请求数、问题段数、GDN chunk 数、读出行数容量；每轮选能装下的最小图，token 紧凑打包、只在尾部 padding（稠密层照算 padding 行但没有有效 token 会访问它们）。轮超过最大图容量就沿请求边界拆成多次重放；单个超大请求直接走无图执行。

几个工程细节值得单独划线。注意力 kernel 从两个来源取键——请求的共享状态和本问题——跳过流里插花的其他请求的状态；tile 表直接在 GPU 上构造，完全可见的键块不加 mask 直读，mask 只施加在部分可见的块上（这也是位级确定性的一部分：直读块与带 mask 读返回相同位）。GDN 层迭代一张定长 chunk 列表，未用满的条目立即返回。改变请求组合只改缓冲区内容，不改任何启动配置——这就是「同一张图吃任意负载」的全部秘密。

这套设计与传统的长度分桶图捕获（SGLang 的做法）是什么关系？论文明确说是在其上构建：分桶捕获解决的是「序列长度多变」一维问题，Flide 把它推广到「树形结构多变」——不仅流长可变，请求边界、问题依赖、检查点位置全都是运行时数据。可以把它理解成把 CUDA 图从「形状模板」升级成「形状模板 + 数据解释器」：重放时 GPU 自己读元数据决定谁看见谁、从哪里继承状态。代价是图族要按容量维度预留（流长、请求数、问题段数、GDN chunk、读出行五个刻度），换来的是任何负载组合零重编译。

§11 位级确定性：可选模式与代价

Proposition 1 保证精确算术下布局无关，浮点下仍有隐患：行数更多的矩阵乘可能选不同的 kernel、tile 形状或归约切分，重排一个输出元素的求和顺序（He & Thinking Machines Lab 那篇批不变推理的经典观察）。Flide 的可选批不变模式让没有任何归约依赖于轮次组成：每个矩阵乘不论行数多少都以固定顺序累加每个输出元素；每个问题拿到自己的 attention tile 和 GDN chunk，归约精确地从分叉点起步。单独问的问题在本模式下就是「状态 + 一个分支」，从完整状态算出的每个答案因此在同硬件同软件的任何负载下保持位级不变。

四个 Qwen 尺寸平均下来，Flide 与 float32 参考的 top 答案一致率（Agr）在每个负载上都是最高：RACE 99.8 对 vLLM 99.5 / SGLang 99.2，QuALITY 99.1，DI 99.4-99.9，MultiRC 99.7。准确率与 vLLM 每格差在 1.2 分以内——快是免费拿的，准没付账。稳定性（Stab）Flide 全列 100.0：单客户端与 64 并发的 top 答案完全一致；vLLM 最多漂 3.2%、SGLang 1.7%、Flide 至多 0.2%（默认模式；不变模式直接 100%）。

真正的审判在 MIS：Table 11 里它的 TV（对 float32 参考）在 0.8B 的 QuALITY 格 14.80 点对 Flide 的 1.11——13.3 倍漂移；四尺寸平均后 QuALITY 上 6.69 对 0.55（12 倍）；0.5 阈值决策的翻转率最坏到 28.9%（QuALITY 0.8B 格），Flide 全表最大翻转 2.3%。Figure 4 的密度图把这件事画得很直观：MIS 的分布整体右移一个数量级，另外三家的曲线几乎重叠。

还有一个容易漏读的指标对：Agr 与 Acc 的分离。Flide 的 Agr 全面最高，但 Acc（对数据集金标准的正确率）三家几乎相同——0.8B RACE 上 67.2/67.2/66.4 之类一格一格都咬得很紧。这说明引擎间的概率漂移大多发生在金标准判对判错的边界之外（题目本身太难或太易，top-1 翻不翻不影响对错），只有把参考换成 float32 隔离计算、把判据换成阈值动作，引擎质量差才显形。给后来者的方法论提醒：评测决策模型服务，拿准确率当指标会系统性低估引擎差异。

手算 5（翻转率的实际含义）。 28.9% 翻转（QuALITY 0.8B 格）是什么概念？这个负载每请求平均 18.1 个问题，一个请求平均翻转 0.289×18.1≈5.20.289 \times 18.1 \approx 5.20.289×18.1≈5.2 个答案；四尺寸平均后 MIS 在 QuALITY 翻转 11.4% 对 Flide 的 1.0%。有个值得玩味的负载差异：MultiRC 上 MIS 的翻转反而温和（0.8B 仅 1.7%），但 TV 仍差 8 倍（3.10 对 0.37）——是非题只有两个选项，top-1 翻转需要概率差越过 0.5，而多选项题在分布漂移下更容易换序。翻转率与 TV 刻画的是两种脆弱性：TV 低保证分布形状、Flip 低保证下游动作。对照论文开头引用的场景——阈值直接作用于概率的部署——拼接换取的吞吐是在用决策正确性付费。这个数字也回击了一种常见辩护：「差一点点概率没关系」——在阈值系统里，差一点点概率就是换一边决策。

§16 消融：四个部件各砍一刀

Table 5 在 Qwen3.5-4B 上逐个拆除部件（引擎内计时、去 HTTP 前端），每行讲一个不同的成本故事：

  • 去扁平图：RACE 吞吐 210.3 → 134.9 req/s（−36%）——每请求单独重放剥掉了「一轮一图」的合并收益；
  • 去选择性读出：各负载 2-8% 吞吐损失——量小但白拿。

§20 批判与边界

三个我认为值得记下的边界。**其一，收益分布不均。**单问题长文负载（QuALITY,1）上 Flide 与最好基线打平（62.3 对 68.6 ms），因为前向计算本身成为瓶颈而那部分谁都要算；摘要的 9.5 倍是结构性多问题负载的上界，不是普遍承诺——论文自己说清了这一点，引用时要带着负载条件。**其二，评测者与被评者的关系。**Flide 与 vLLM 读同一 prompt、SGLang 自带模板，MIS 关 CUDA 图是它机制使然——基线配置大体公允，但「对比生成引擎的决策端点」本身有口径差（Table 13 的 endpoint vs token id 两行就是在补这个洞，加分）。**其三，单卡单客户端世界。**所有实验一张 H200、闭循环客户端至多 64；多卡分片、连续 batching 与生成流混跑、优先级抢占这些生产 serving 的复杂度未触及——「决策专用引擎」在真实集群里如何与生成负载共存，是留给下一篇的问题。另有一点工程现实：扁平图的固定容量族意味着内存上界按最大图预留，18.8 GiB 里 2.1 GiB 是图——小卡部署时这比模型权重更值得先算。

§21 paper-check 自测

Q1（概念）：为什么 GDN 层不能像全注意力层那样用 mask 隔离兄弟问题？ A1：mask 只能屏蔽「还没进入计算的信息」。全注意力里每个查询显式读取键集合，mask 改变可见集即可；GDN 把之前所有 token 折叠进单一循环状态 SSS，第二个问题开始递推时兄弟的信息已经溶在 SLsS_{L_s}SLs​​ 之后的继承链里，没有可屏蔽的显式读取路径。必须让递推从躯干末尾状态 SLsS_{L_s}SLs​​ 重启（两次调用 + 状态索引），而不是事后遮蔽。

Q2（计算）：状态 2,000 token、64 个问题各 20 token。朴素法与 Flide 的 token 计算量各多少？比值？ A2：朴素 64×(2000+20)=129,28064 \times (2000+20) = 129{,}28064×(2000+20)=129,280；Flide 2000+64×20=3,2802000 + 64 \times 20 = 3{,}2802000+64×20=3,280；比值 39.439.439.4。问题越密，式 (2) 两项的差距越大——这是 Figure 5a 陡峭对照的解析版。

Q3（改输入）：把 Q2 的问题数减半到 32，其他不变，比值变多少？说明什么？ A3：朴素 32×2020=64,64032 \times 2020 = 64{,}64032×2020=64,640，Flide 2000+640=2,6402000 + 640 = 2{,}6402000+640=2,640，比值 24.524.524.5。比值从 39.4 降到 24.5：共享越薄（问题少、状态短），结构性收益越小，极限是单问题时比值收敛到 1——这正是 Table 3 里单问题负载只剩执行层优势的原因。

Q4（数据）：MIS 在 QuALITY,all 的 0.8B 格 TV 是多少？对 Flide 同格几倍？翻转率对比？ A4：Table 11 Qwen 0.8B QuALITY（all questions 口径列）MIS TV 14.80、Flip 28.9%；Flide TV 1.11、Flip 2.1%。倍数 14.80/1.11≈13.314.80/1.11 \approx 13.314.80/1.11≈13.3；翻转差 28.9/2.1≈13.828.9/2.1 \approx 13.828.9/2.1≈13.8 倍。分隔符的「一个 token」代价在分布层面放大了一个数量级。

Q5（机制）：为什么改变请求组合不需要重新捕获 CUDA 图？ A5：因为所有组合相关变量（段长、位置、键范围、状态索引）住在 GPU 常驻缓冲区，kernel 启动形状只由流长决定。捕获时按流容量建图族，重放前填缓冲区即可——组合是数据，不是形状。

Q6（应用）：一个 agent 每步 50 新 token、决策间隔阈值 5 ms/步（1B 级模型）。Flide 能撑多长历史？ A6：按 Table 7 的 0.8B 斜率 0.88 ms/千 token 与 <4k 时 11.7 ms 基线：延迟 ≈11.7+0.88×H千\approx 11.7 + 0.88 \times H_{\text{千}}≈11.7+0.88×H千​。5 ms 阈值下 H≤(5−11.7)/0.88<0H \le (5-11.7)/0.88 < 0H≤(5−11.7)/0.88<0——即 0.8B 单 agent 在该斜率下基线已超 5 ms；但 32 agent 并发时 Flide 每步 208.2 ms/32 agent ≈ 6.5 ms/agent·步。若阈值指单步 wall-clock（并发摊销后），1B 级在 16k token 内可守住约 6-19 ms/步区间，对比 vLLM 的 56-98 ms/步仍有近一个数量级余量。要点：这类估算必须先明确阈值是单请求延迟还是摊销吞吐，两者在闭循环并发下差 3-10 倍。
