深读对象：HarnessPro: Recursive Harness Self-Improvement with Pareto Optimization for Performance-Cost Trade-offs（arXiv 2610.26770v2，PDF 41 页，清华、Z.AI、上海交大、Warwick、Kling AI 合作）。Harness 递归自我改进（RSI）这一线的方法都在回答"怎么让 Agent 的编排层自己变好"；这篇论文换了一个部署视角的问法：变好的每一步都在花钱，钱进不进目标函数？ 此前的无标签方法 RHO 在 SWE-Bench Pro 上把通过率从 59.0 提到 80.0，代价是单任务成本涨 42.6%。HarnessPro 把目标改成带性能地板的双目标 min(−PR, C)，用多智能体管线做递归进化，输出 lite/medium/heavy 三档 harness 而非单一产物：GPT-5.5×Codex 上 heavy 档三基准全部超过 RHO 且平均成本低 26.1%，medium 档在 SWE-Bench Pro 上用一半价格保住 RHO 级性能。本篇按细章深读规范逐段重构：机制逐一展开、公式逐步推导、主表逐列验算、附录 B/C/D（进化指令、智能体产物、进化后 harness 的完整配置）全部整合进正文。

01 / 问题：RSI 的账单从来没有进过目标函数

Harness 是模型外围的软件运行层：提示、工具与技能、上下文与记忆机制、hooks、验证策略。RSI 路线（RHO、AHE、HarnessFix、HarnessX）用历史执行轨迹诊断弱点、指导 harness 更新，但它们的目标函数里只有通过率一个变量——更强的探索、更深的验证是唯一被奖励的修改方向，token 与延迟的膨胀是"副作用"，从没有人把它请进优化目标。论文的动机数字值得亲手验算一遍：RHO 在 SWE-Bench Pro 上把成本从 $1.88 推到 $2.68，涨幅

(2.68−1.88)/1.88=0.800/1.88=42.6%(2.68-1.88)/1.88=0.800/1.88=42.6\%(2.68−1.88)/1.88=0.800/1.88=42.6%

分母是旧成本。也就是说涨掉的 80 美分是每个任务、每次运行的经常性支出。部署视角下这就不可接受了：一个通过率 80 分但单任务 $2.68 的 harness，和一个 79 分但 $1.26 的 harness，多数真实场景会选后者——但现有方法根本不生产后者。

于是论文的问题式（Eq. 1）是全文一切设计的源头：

min⁡h∈H  (−PR(h), C(h))s.t.PR(h)≥PR(h0)\min_{h\in\mathcal{H}}\;\big(-\mathrm{PR}(h),\,C(h)\big)\quad\text{s.t.}\quad \mathrm{PR}(h)\geq \mathrm{PR}(h_{0})h∈Hmin​(−PR(h),C(h))s.t.PR(h)≥PR(h0​)

三条承诺叠在一起：找的是帕累托前沿而不是单点；初始 harness h0h_0h0​ 的通过率是硬地板；最终交付前沿上的三个代表（lite/medium/heavy）而不是一个"最优"。后文会看到，这个式子如何把整条流水线的设计串起来。

定位上也值得对齐一下（Table 1 的四维比较）：优化目标（Pass 还是 Pass+Cost）、修改范围（技能/工具还是整个 harness）、反馈来源（有无真值标签）、迭代方式（单轮还是递归）、产出（单一还是帕累托集）。此前没有一个方法同时满足"双目标+全 harness+无标签+递归+帕累托集"：SkillMOO 双目标但只优化技能文档且依赖真值；RHO 无标签但单轮、单目标、单产出；AHE 递归修改整个 harness 但需要真值。HarnessPro 的贡献是把这个组合第一次凑齐——而凑齐的难点恰恰在"无标签 × 双目标"的交点上：没有真值时性能地板怎么量、双目标时没有标准答案的候选怎么比，这分别是 §04 与 §10-11 要解的两个题。

02 / 三个指标各怎么算

通过率与三集隔离

任务通过的定义是全部官方测试通过（ProgramBench 例外：按官方协议取每任务通过测试比例的宏平均）。ProgramBench 的口径差异要说清：宏平均先算每个任务自己的通过比例、再对任务等权平均——一个只通过一半测试的任务贡献 0.5 而不是 0，所以它的数字与"全过式"基准不可直接比大小，只能比同基准内的相对变化。数据切三份：训练集（10 个任务，见 §05）驱动进化、验证集评估候选与选代表、测试集只在全部进化结束后评估一次。三集隔离不是走过场——§06 会看到验证集与测试集对 Planner 全程不可见，测试集指标在 Fig. 4 里逐轮画出但仅作可视化，不参与任何选择。

墙上时钟、评分时间不计。论文明确不把它放进目标：服务器负载与网络会污染它，同一配置早晚跑两遍延迟就能差出成比例——一个被噪声污染的目标会把选择压力引向运气好的那轮。但结果里它普遍改善了（SWE 上 heavy 档 520s→412s）——省 token 的动作大多也省时间，这是红利不是承诺。

03 / 地板约束：为什么"不伤性能"必须是硬约束

回到 Eq. 1 的约束项。如果没有 PR(h)≥PR(h0)\mathrm{PR}(h)\geq\mathrm{PR}(h_0)PR(h)≥PR(h0​)，双目标优化有一个天然的下坡路：把推理力度锁到 low、砍掉全部验证、清空上下文——成本骤降，通过率也骤降，但只要它还在帕累托前沿上（更便宜但更差），选择器就没有理由拒绝它。Table 3 给了这个退化的实测版本：给 RHO 加"固定低推理力度"，Terminal-Bench 2 成本从 $1.09 降到 $0.45（−58.7%），通过率从 76.3 崩到 62.7。地板量的是验证集上的通过率（h0h_0h0​ 用固定生成测试在 Dval\mathcal{D}_{val}Dval​ 上跑出的 PRval(h0)\mathrm{PR}_{val}(h_0)PRval​(h0​)），不是测试集——地板本身也建立在生成测试这把尺子上，尺子的漏检会传导为地板的松动（§16 回到这一点）。它的作用是把整个搜索空间切掉一半：只在"不比初始差"的区域内找便宜解。这个设计在附录 B 的进化指令里还有第二重保险（§08）：指令文本明说"要真实的效率收益，而不是靠跳过必要工作、放弃困难任务或弱化验证换来的低账单"。

04 / 无标签评估：把判官换成一把固定的尺子

判官的乐观偏差

无标签设定=没有真值解、官方测试、判分器。RHO 用 LLM 对比轨迹做自偏好选择。论文的观察：LLM 判官系统性乐观——经常把有缺陷的实现判成成功。这不是抽象批评：合并训练任务的混淆矩阵（Fig. 2）给出量化，直接 LLM 判断的失败检出率只有 41.7%，即一百个失败任务里 58 个被当成成功放行。偏差的方向值得点破：判官看到的是一条"叙述自洽、步骤完整"的轨迹——模型执行得有条不紊，只是结果错了；判官评估"过程像不像成功"而非"产物真的满足要求"，于是系统性把"执行得漂亮的功能性失败"放行。在单目标 RHO 里这个偏差直接虚增感知改进：候选被高估的分数进入选择，选出的 harness 再被同样的偏差复核，误差不复原、只累积。

测试合成器的完整规程

HarnessPro 的替换是把 LLM 从"裁判"降级为"出题人"：

S(x)=TestSynth⁡(x, τh0(x))\mathcal{S}(x)=\operatorname{TestSynth}\big(x,\,\tau_{h_0}(x)\big)S(x)=TestSynth(x,τh0​​(x))

输入是任务描述与初始 harness h0h_0h0​ 的轨迹，一次性生成后全程固定。附录 C.3 的部署规程比正文详细得多，四个要点值得展开：证据边界——只读 public-task.json、public_inputs 与只读的初始产物，产物"只是实现与执行诊断的上下文，永远不是答案钥匙"，明令禁止寻找官方测试/判分器/解法（本地或在线）；出题纪律——覆盖文档化的行为、有效替代、边界与合理组合，"不要为了凑满固定数量发明额外义务"——凑数的用例只会稀释尺子的分辨力；oracle 选择阶梯——优先公共参考 > 已知答案 > 必要内容性质 > 可判别的元变换关系（元变换指"对输入做一类已知变换、输出应按同样规律变化"的性质，它不需要知道标准答案也能判对错），且"永远不从被测产物推导期望常数、哈希或容忍值"（否则测试就成了循环论证）；执行语义——status=ok 而 passed=false 是"合法执行+产品失败"，让产品通过不是目标；infra_error 才是待修的测试缺陷，且只修"被证实的缺陷"、不跳用例、不捕获所有异常、串行执行。输出契约固定为恰好 10 个用例 + 清单（每例标注 behavioral/format/unavailable_oracle）+ 覆盖记录（含"没检查什么"）+ 修复日志。

为什么从 h0h_0h0​ 的轨迹出题

测试合成的输入是初始 harness 的轨迹而非各候选的轨迹，这是设计而非便利：若从候选轨迹出题，测试会随候选漂移，"固定"就名存实亡。h0h_0h0​ 轨迹在这里的角色被规程严格限定——它是"实现与执行诊断的上下文"，帮助出题者理解任务的输入输出接口长什么样，但"永远不是答案钥匙"：期望值必须来自公共证据（文档、已知答案、内容性质），不从产物推导。这留下一个隐含的边界：h0h_0h0​ 越弱，其轨迹能提供的接口信息越少，出题质量越依赖任务描述本身——论文的 h0h_0h0​ 是 Vanilla（原始 Codex/Claude Code harness），已是不弱的起点；对极弱初始 harness 的行为，论文未做检验（§16）。

"固定"的两重作用

固定测试既是公平性机制（所有候选被同一把尺子量），也是防作弊机制：进化不能通过"让判据变松"伪造进步——这恰是 RSI 可信框架里"修改改进机制"风险的工程化防御。换用固定测试后失败检出率升到 83.3%。混淆矩阵原文：

06 / epoch 循环总览：Algorithm 1 逐段走查

整个框架是一个三阶段循环，初始化只有四件事：收集 h0h_0h0​ 在 train∪val 的轨迹；对每个任务生成固定测试 S(x)\mathcal{S}(x)S(x)（一次生成，永不再改）；用 S\mathcal{S}S 量出 h0h_0h0​ 的验证通过率立为地板；候选集 A0={h0}\mathcal{A}_0=\{h_0\}A0​={h0​}。此后每轮：

阶段一（诊断）：每个候选在 10 个训练任务上各跑 G=3G=3G=3 条独立轨迹，Analyzer 联合检查轨迹与指标（§07）；阶段二（生成）：每个候选 × 三种优先级指令出三份计划（§08），Editor 在独立工作区各落一个可执行 harness、Git 提交，新候选与父代合并成 C~t=At∪Ct\widetilde{\mathcal{C}}_t=\mathcal{A}_t\cup\mathcal{C}_tCt​=At​∪Ct​；阶段三（评估选择）：每个候选在验证集每任务跑一次、固定测试判分，先滤掉破地板或被支配者，再为三档各选一个代表组成下一轮 At+1\mathcal{A}_{t+1}At+1​（§10–11）。轮数：TB2 与 SWE 各 3 轮、ProgramBench 4 轮；候选集每轮最多 3 个（三档代表），因此每轮产生至多 3×3=9 个编辑候选，加上 3 个父代共至多 12 个 harness 要在验证集上各评估一遍——验证集规模直接决定每轮的评估账单，这也是训练侧只用 10 任务做诊断、把大批任务留给验证的原因之一（诊断要 G=3 遍重复，单任务成本是验证的 3 倍以上）。

Analyzer 的输出是结构化的问题清单：每条问题含问题描述、对性能与成本的影响、证据定位（轨迹文件路径+事件行号区间），按任务汇总超 64K token 再摘要一层。附录 C.1 给了两份真实产物，恰好展示诊断的两种形态。

失败侧样例：Caffe–CIFAR-10

任务"构建 CPU 版 Caffe 并训练 CIFAR-10 五百轮"，三条轨迹全部在训练前止步。诊断给出五条问题：Issue 1（共享瓶颈）：三轨分别卡在 protobuf 修复、Caffe 已建成但在下载数据集、OOM 后重建中——"全部止步于训练前"这个共性被从三条不同表象里抽象出来；Issue 2（成本）：make -j$(nproc) 高并行编译在每条轨迹都触发 OOM，失败的编译轮次是纯浪费；Issue 3（个别失速）：最先进的一条打断单流下载换 aria2 并行下载，装好了工具却在下载中结束；Issue 4 最值得注意——一个"未观察到的下游风险"：一条轨迹的 Caffe 配置没开 OpenCV，而标准 CIFAR 流程的 compute_image_mean 需要 OpenCV，"如果跑到那一步大概率会失败"——诊断不只记录已发生的失败，还推演将要发生的阻塞并给出证据行号；Issue 5（无害扰动）：误用不存在的 1.0.0 分支后自行检查 tags 改用 1.0，标注为"增加了命令但无持久质量损失"。这份清单给下游 Planner 的信号非常具体：这里有可避免的编译浪费（Issue 2）、有下载策略问题（Issue 3）、有配置缺陷（Issue 4）——每条都同时标注了质量影响与成本影响。

成本侧样例：Mailman

对照样例是 Postfix/Mailman 3 邮件列表配置任务，三条轨迹全部通过生成测试，但诊断照样列出问题：探索远超相关配置的范围（把与任务无关的系统状态也检查了一遍）、对同一配置点的重复检查、以及两次不改结局的绕路（装了不必要的组件又回退）——全部标注为"增加成本而不改变最终结果"。这显示了双目标框架下的诊断视角：通过的任务也要审账。RHO 式单目标管线没有动机为全过的任务写诊断。

附录 B 的三条指令说了什么

三条指令（I1I_1I1​ 省成本 / I2I_2I2​ 平衡 / I3I_3I3​ 重性能）的原文比"优先级不同"这个概括有信息量得多。I1I_1I1​ 的核心句："追求真实的效率收益，而不是靠跳过必要工作、放弃困难任务或弱化验证换来的低账单……更少的步骤或更短的输出本身不构成改进"；I2I_2I2​："把正确性与效率当联合目标……平衡的计划应当改进权衡，而不是简单平均另外两个方向"；I3I_3I3​："把投入集中在能解决实质性失败的地方，而不是在所有任务上均匀加算力……不要假设更复杂的 harness 就是更有能力的 harness"。更关键的是三条共有的元要求："这些都是可选的搜索方向而非清单——从证据推导机制，不要预设路由规则、固定阈值、档位分类法或逐任务规则"。这一点常被误读：论文正文 §5.3 展示的五档执行档位不是设计者写死的，而是 Planner 在证据下自己长出来的——指令只给方向与边界，机制由数据决定。为什么要把话说得这么死？因为一旦指令预设了机制（比如"做一个路由器"），Planner 就会照做——进化将收敛到设计者的想象而不是证据；且预设机制在错误基准上是系统性浪费（§15 的 ProgramBench 产物证明了这种担心的现实性：那个基准上根本不该有路由）。§15 会看到三基准进化出的产物结构确实不同。

12 / 主结果：把每个百分比验算回去

六条基线各控制什么

先把对照组的身份摆清，否则数字读不出归因力。Vanilla 是优化起点（原始 Codex/Claude Code harness）；Dynamic Cheatsheet 维护跨任务复用的策略与代码片段本；ReasoningBank 从历史轨迹蒸馏策略库按任务检索；Sleep-time Compute 在查询到来之前预先对上下文做推理、把结论存成可复用记忆——这三条代表"记忆/经验复用"路线，不修改 harness 本体。RHO 是最接近的前身：轨迹分析指导修订技能与工具、LLM 自偏好选候选、单轮单目标。Balance 只把 RHO 的优化指令改成双目标（框架不动）——它拆开"指令"与"框架"的贡献；RHO+Iteration 让 Balance 跑满与 HarnessPro 相同的轮数——它拆开"递归"与"双目标机制"的贡献。这两个变体是全文归因设计的支点：若 Balance 就够用，HarnessPro 的多智能体框架就是多余的；若 RHO+Iteration 能追平，双目标选择机制就是多余的。结果（§13）显示两者都不够。

GLM-5.2×Claude Code 同型成立：TB2 heavy 81.4/$0.62 vs RHO 78.0/$1.00（+3.4 分且便宜 38%）；SWE heavy 77.3/$1.01 vs RHO 75.0/$2.17（+2.3 分且便宜 53%）；PB heavy 64.4/$14.95 vs RHO 63.3/$17.00。但两基座价目不同（GLM 输出 $4.40/M vs GPT $30.00/M）且缓存行为不同，GLM 在 PB 单任务 $11–17 的绝对值与 GPT 侧差一个量级——结合 §02 的分析，这是 GLM 思考型执行的 token 体积所致，跨基座美元只能比相对变化。另注意 heavy 在 SWE 的 +0.7 分在三次运行的样本标准差量级内，"更便宜"比"更好"证据更硬；GLM 侧的分差更大（+2.3/+3.4），提示方法在"基座更啰嗦"的组合上省得更多。

13 / 演化动态：双改善常要等到第二轮之后

Fig. 4 逐轮画测试集指标——注意这些中间点只用于展示演化轨迹，任何一轮的过滤与代表选择都只用验证集数字，测试集曲线如果反过来影响选择就构成泄漏，论文在图注里专门声明了这一点。TB2 的 heavy 一路双改善：74.6/$0.91 → 80.8/$0.72；lite 与 medium 第 2→3 轮守住分数继续降本（$0.61→$0.43、$0.68→$0.56）。最有信息量的是 SWE medium 的三轮：70.0/$1.57 → 77.0/$1.66（涨分也涨钱）→ 79.0/$1.26（双改善）。单轮进化常只买到"分或钱"之一；双改善是递归多轮+帕累托选择压力的产物。对照 RHO+Iteration（同轮数、单目标指令）：TB2 上 medium 与它同分（76.3）但便宜 (0.82−0.56)/0.82=31.7%(0.82-0.56)/0.82=31.7\%(0.82−0.56)/0.82=31.7%，SWE 上它 80.0/$1.90 仍被 heavy 80.7/$1.97 在分数上压过，PB 上 heavy 比它高 1.3 分再便宜 5.8%。读法要点：RHO+Iteration 证明了"多跑几轮"本身也能省点钱（TB2 从 1.09 降到 0.82），但它的选择器是单目标的，每轮只朝一个方向收敛，永远到不了前沿的另一半——同轮数救不了单目标，功劳在双目标规划与前沿筛选。ProgramBench 的第 4 轮各档继续降本保分，说明在任务同质度高的基准上，多轮递归的价值形态不同：不是继续涨分，而是持续挤出同质任务上的冗余开销。延迟维度再补一笔：medium 档在 TB2 上 253s、SWE 上 326s，均低于 RHO 的 354s/437s——成本优化经由"少生成、少重复检查"几乎必然带出速度收益，但论文不承诺它，读者也不应把它当选择依据。

14 / 消融：尺子与药方各值多少

CoP 也让消融更可读：SWE medium 去 Planner 后 CoP 从 $1.59 涨到 $1.95——每个成功任务贵了 23%，因为掉分与涨价同时发生。去 Planner：SWE medium 79.0/$1.26 → 73.0/$1.42——分数掉、钱反升，说明三档计划是"找到双改善方向"的来源，没有它编辑只在单方向上用力。去测试合成器：三档全线掉 3.4–10.0 分（heavy TB2 80.8→74.6），掉幅最大——尺子不可靠一切白搭，这是无标签框架的承重墙。更有归因力的是"RHO 抄单机制"三变体：+动态路由（TB2 76.3/$0.92、SWE 76.0/$2.13）、+预算 hooks（76.3/$0.92、75.0/$1.75）都省钱但都掉分；+固定低力度掉最惨（62.7/$0.45）。三个变体全部被 HarnessPro 帕累托支配——双改善是组合机制+递归选择的涌现性质，把任何单件搬到单目标框架都退化为单边受益。

15 / 进化解剖：钱省在哪（附录 D 全量）

五档执行档位与门控路由

TB2 medium 进化产物是四个文件：model_instructions.md、profile_rubric.md、policy.json、hook.py。一个独立的 GPT-5.5 调用按 rubric 从任务描述选五档之一，policy 落参数，hook 执行预算。五档（medium 模式）：compact（low 力度，收敛≈4 次调用/停止≈8）、lean（low，10/16）、standard（medium，26/38）、deep（high，30/48）、research（high，约 40 次）。rubric 的门控顺序 compact→research→deep→lean→standard，其中两处设计高于直觉："未知决定性证据默认 standard"（信息不足不许降档）；强 oracle 的定义极其严格——必须显式可本地重复且提供局部化失败/定量误差/候选排序/确定性仿真之一，"编译通过、端口开了、跑通一次端到端"明确算弱证据。deep 档列出九种适用形状并同样列出不适用清单——适用侧的公共内核是"存在可局部验证的强假设生成-检验循环"：潜结构/参数恢复（有精确兼容性或定量目标）、跨多组件的状态一致性（可用不变量或往返检查）、损坏结构状态恢复（竞争性格式/排序假设）、带可执行评分器的约束合成、从大量观测做精确候选验证的恢复/推理/攻击、带确定性模拟器的逆问题、确定性变换下的候选构造、双语法双重有效性、严约束下的参考行为重实现；不适用侧一句话总结：术语查证、长规格阅读、普通性能调优、普通逆向、只有隐藏测试都不是 deep——以及"deep 需要容得下几次改变证据的迭代"，如果评估本身吃掉大半个时限，再强的 oracle 也支撑不起 deep。compact 门控同样列了五种形状（视觉/隐藏状态的长串行交互、不可用的账号设备凭据、宽泛隐藏行为+端到端接受拒绝联合目标、单工件跨多语法仅联合反馈、无量化比较器的海量媒体判读），并强调"难、可视化、专项化、虚拟化本身不够格"。

hook.py 逐段

预算不是建议是硬闸：_pre_tool_use 计数超过 finalize_after_tools 时直接 permissionDecision: deny，拒绝语是行为指令："保留当前文件，停止调用工具，基于现有证据给出最佳最终答案"。两段阶段提醒：economy_after_tools 处触发"经济期开始：批量独立检查、停止过程叙述、不重复未变的检查、不要拿任务要求的行为验证或精确终态检查做交易"；strict_after_tools 起每 strict_reminder_every 次重申"收敛期：停止广泛探索……若有具体失败未解或交付物被改，修复它而不是因为进入该阶段就收尾"。_compact_text 做行级去重（重复超过 2 行折叠为"[前行又重复 N 次]"）+首尾截断。

lite/heavy 与另两个基准的差异

lite 只改 policy：deep/research 力度 high→medium、各档 finalize 全线下调（14→8、22→16、44→38、54→48、46→40）——同 rubric 同 hook，靠参数降档。heavy 反向：rubric 与 policy 双双上调——compact 变 4/8/14、lean 升为 medium 力度 10/22/36、standard 升为 high 力度 18/38/60、deep 20/42/68、research 16/36/60——lean 门槛放宽到"约 12 次或更少证据调用"，指令里加强多阶段服务的外部入口验证与"收尾前重读公共任务一遍、对照独立证据核对每项要求"。SWE 产物多了两件 TB2 没有的东西：bin/repair-verify（通用代码检查脚本）与 checklists/contract-verification.md（逐项契约核对清单），工作流是一套仓库修复的契约化纪律：先把 task/prompt.md 当契约读、为一组"精确公共名字"（文件、负载、默认值、错误行为、兼容性要求、明说的边界情形）记账本；改动前先查本地 git 历史、tags、上游提交、相邻实现——"已知修法优先适配，不猜"；做满足契约的最小生产源码改动；预留预算给改后任务形态测试与最终 diff 核对，"仅编译通过不足为凭"；生成物、缓存、临时测试不得进最终补丁。ProgramBench 产物则完全没有路由：固定 GPT-5.5 high 力度，取而代之的是七步"证据优先重建流程"：把随附文档全部读成行为台账（命令、旗标、输入输出、退出码、文件效应、默认值、错误行为、格式、明说的边界）；尽早立起 compile.sh 与最小可执行骨架、先跑通完整构建-运行循环；只经公共接口对参考实现做小判别性探针、记录实测而非按程序名臆断；先广度后打磨（快乐路径与常见输入类优先）；自建用例双向对拍，分歧要约化出一般规则而不是打特例补丁；定期从干净状态重建——依赖缓存产物、未声明工具或提交目录外文件的"解"不算完成；最终离线验证 compile.sh 可执行、代表性成败探针与参考一致。三基准产物结构不同恰好证明附录 B 的元约束：机制由证据决定，没有预设模板。读者复用这套框架时也可以据此预判：你的基准任务如果高度同质，进化的产出大概率是"流程纪律"而不是"路由结构"；异质任务集合才会养出门控路由这类自适应机制。

16 / 证据的边界

四条边界。尺子上限：83.3% 检出率意味着约 1/6 失败被漏检，且漏检不是随机的——固定 10 个用例的预算天然偏向行为主路径，风格退化、性能回归、用例没覆盖的部分行为这类失败最容易被放过；出题又只看得到 h0h_0h0​ 的一个实现视角，接口的未见侧面可能根本没人测。进化过程中的地板与支配判断建立在这把有误差的尺子上——靠测试集官方测试的最终评估兜底结论，但进化路径可能被误导；coreset=10：诊断覆盖面系于 DPP 选样，未见失败模式进不了诊断；成本口径：固定价目+各基座缓存行为不同，跨基座不可横比；CoP 与成本的换算依赖价目表时效；结论范围：heavy 在 SWE 的 +0.7 分在噪声量级，三基准都是"任务-工件-通过"型，对话式或开放探索型任务未覆盖。复现条件方面附录 A.2 齐备：默认力度（GPT-5.5 全程 high；GLM 在 TB2/SWE 用 max、在 PB 降到 high 因 max 会拖长执行）、求解器时限（TB2 原生 600–3600s；SWE GPT 1200s/GLM 7200s、判分 3600s；PB 求解 7200s+判分外层 14400s）、环境（8 CPU/32GiB）、生成参数（Codex 走 Responses API 不显式设温度与 top-p、GPT-5.5 单响应最大 128K 输出 token；GLM temp 1.0、TB2/SWE 用 top-p 0.95 与 131,072 max_tokens，PB 改 top-p 1.0、32K token、2,000 轮上限——PB 的收紧再次指向思考型执行的体积问题）。评测侧温度 0.7/top-p 0.95、每基准至少两次运行取均值（TB2/SWE 三次、PB 两次），HarnessPro 的波动以样本标准差呈现在 Table 2。

17 / 接回论证

把链条合上：换尺子（固定生成测试，检出率翻倍且封死改判据的自欺）→三向施压（三优先级计划让每轮搜索同时朝性能与成本两个方向探索）→前沿筛选（地板+支配过滤保证只进不退，平方距离把前沿落成三个可部署代表）→产物证据（进化出的不是"少读点上下文"而是档位路由+硬预算闸+输出压缩+契约核对的组合，且三基准各自长出不同结构）。RHO 证明了无标签 harness 进化能涨分；HarnessPro 证明同一套原料在目标函数里放进钱之后，能同时把"更好"与"更便宜"做出来——自我改进从能力问题推进到了经济问题，而部署要的正是后者。留下的问题同样清楚：生成测试的尺子还能不能再准（83.3% 不是上限）、coreset 能不能扩到更便宜的评估预算所允许的规模、以及当被优化的 harness 本身开始生成评估用的测试时，这把尺子与被测者的边界要怎么守住——最后这一问，正是 RSI 可信框架留给这个方向的下一题。

理解自测

六个能检验技术理解的问题

  1. 去掉地板约束最可能退化成什么？论文里哪个变体是这个退化的实测？

    想想哪种修改最便宜；Table 3 里 RHO+固定低力度。

    展开参考答案

    退化为砍计算换低价：低力度变体成本 1.09→0.45（−58.7%）但通过率 76.3→62.7。地板把搜索锁在不伤性能区域内；附录 B 指令文本（不靠跳过必要工作换低账单）是第二重同向保险。

    PDF Eq.1、§5.5、附录 B

  2. 成本教学例里输出 token 只占约 4.4% 却占成本 55%。把缓存输入从 0.30M 提到 0.40M（其余不变），成本怎么变？这说明什么策略最伤钱？

    按价目表逐项算：5×0.05 + 0.5×0.40 + 30×0.016。

    展开参考答案

    0.25+0.20+0.48=0.93 美元，只涨 5 美分（缓存输入单价仅 0.50/M）。真正伤钱的是输出量与无限拖长的对话尾巴——这就是 hook 预算闸存在的原因：它同时限调用数（间接限输出）并在超限时强制收尾。

    PDF Table 4、§15 hook；教学重算

  3. 固定测试的『固定』防住哪两种作弊？若每轮允许重新生成测试，进化会往哪个方向跑偏？

    展开参考答案

    防：候选间尺子不一致（不公平比较）；改判据伪造进步（让测试变容易而非 harness 变好）。允许重生成时，进化方向会偏向拟合当前候选的行为特征——尺子与被测者共同演化，地板与支配过滤全部失真。这对应 RSI 可信框架里修改改进机制层的风险。

    PDF §4.3

  4. Eq.9 教学例中把 heavy 权重从 (2,1) 改成 (3,1)，两候选的 J 各是多少？结论变吗？为什么？

    d_perf 甲=1 乙=0；d_cost 甲=0 乙=1。

    展开参考答案

    甲 J=3，乙 J=1，heavy 仍选乙。乙在性能维已是归一化最优，加大性能权重只会放大甲的劣势，无法压低乙的成本惩罚。权重真正起作用的场景是两维都非零的中间候选之间排序。

    PDF Eq.8-9、附录 A.2；教学重算

  5. 『成本平均降 26.1%』如果换成按测试集题量加权的总成本口径，数字会变吗？往哪个方向变？

    三基准降幅 33.9/26.5/17.8，题量 59/100/100，RHO 成本 1.09/2.68/3.59。

    展开参考答案

    会变。加权总降幅 =(1.09×59+2.68×100+3.59×100−0.72×59−1.97×100−2.95×100)/(1.09×59+2.68×100+3.59×100) ≈ (64.3+268+359−42.5−197−295)/691.3 ≈ 157/691.3 ≈ 22.7%——降幅最小的 ProgramBench 题量与成本双大，拉低加权值。两种口径都合法，引用需注明。

    PDF 摘要、Table 2、§5.1；算术重构

  6. TB2 产物有五档路由，ProgramBench 产物却是固定 high 力度、无路由。这个差异证明了框架的哪个设计主张？

    展开参考答案

    附录 B 的元约束：指令只给方向（可选搜索方向、不预设路由规则/档位分类/逐任务规则），机制必须从证据推导。ProgramBench 任务同质度高（程序重建），路由的判别价值低而其分类调用本身是净开销，固定档位+重建流程才是证据支持的解；TB2 任务异质，档位路由才划算。三基准产物结构不同正是该主张的实证。

    PDF 附录 B、D.1、D.3
